# Story 1.2: Cadastro de Produto e Templates de Categoria

## Status
Done

## Complexidade
**M** (Medium) — Formulário com lógica de template dinâmico, API Route, validação client+server.

## Dependências
**Requer:** Story 1.1 (tabelas `mvp_products`, `mvp_stages`, `mvp_category_templates` devem existir).

## Escopo
**IN:** Formulário de cadastro, carregamento de template por categoria, edição de etapas (adicionar/remover/reordenar), API de criação, listagem em `/produtos`.
**OUT:** Drag-and-drop avançado (usar botões up/down no MVP). Edição de produto após criação (story futura). Upload de imagem de produto.

## Riscos
- **Template desatualizado:** Se `mvp_category_templates` estiver vazio (seed não aplicado), formulário quebra. Mitigação: tratar estado vazio com mensagem de erro clara.
- **Reordenação de etapas:** Lógica de `ordem` pode ter bugs com adição/remoção simultânea. Mitigação: recalcular `ordem` sequencialmente ao salvar.

## Story
**As a** gestor,
**I want** cadastrar um produto e ter as etapas pré-preenchidas pela categoria,
**so that** eu não precise criar o fluxo de produção do zero a cada novo produto.

## Acceptance Criteria
1. Rota `/produtos/novo` acessível no App Router com formulário funcional
2. Campos obrigatórios: nome, categoria (dropdown), canal de venda, quantidade, data de início planejada
3. Ao selecionar categoria no dropdown, etapas padrão carregam automaticamente com datas sequenciais sugeridas (baseado na duração de cada etapa do template)
4. Etapas são editáveis antes de salvar: reordenar via drag-and-drop (ou botões up/down), adicionar nova etapa, remover etapa existente
5. Ao submeter, produto e etapas são salvos em `mvp_products` e `mvp_stages` respectivamente
6. Produto salvo aparece em `/produtos` na listagem geral com status "Planejado"
7. Validação client-side e server-side: campos obrigatórios, data válida, quantidade > 0. Mensagens de erro claras

## Dev Notes

**App Router path:** Projeto usa `app/(dashboard)/` para páginas autenticadas. Nova rota: `app/(dashboard)/produtos/novo/page.tsx`.

**Auth:** Usar `getServerSession(authOptions)` de `lib/auth.ts` (padrão do projeto existente). `user_id` NUNCA vem do cliente.

**Components:** shadcn/ui já instalado. Usar: `Input`, `Select`, `Button`, `Label`, `Card`. Localização: `components/ui/`.

**API Routes pattern:** Projeto usa `app/api/[resource]/route.ts`. Nova route: `app/api/mvp/products/route.ts`.

**Supabase client:** Server-side usa `createClient` de `lib/supabase/server.ts` (padrão SSR do projeto).

**Imports absolutos:** Sempre usar `@/` (ex: `@/components/ui/button`, `@/lib/supabase/server`).

**Drag-and-drop:** Se usar biblioteca, preferir `@dnd-kit/core` (leve). Alternativa simples: botões up/down para MVP.

**Testing:**
- Framework: vitest + `@testing-library/react`
- Arquivos de teste em `__tests__/` ou co-located `*.test.tsx`
- Testar: renderização do formulário, carregamento de template, validação
