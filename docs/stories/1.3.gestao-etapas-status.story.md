# Story 1.3: Gestão de Etapas e Status

## Status
Done

## Complexidade
**M** (Medium) — Transições de status, integração com audit_logs existente, lógica de "atrasada" server-side.

## Dependências
**Requer:** Story 1.2 (produtos e etapas devem existir para avançar status).

## Escopo
**IN:** Transições Planejada→Em Andamento→Concluída, badge Atrasada automático, histórico via audit_logs, progresso % no topo.
**OUT:** Notificações por email ou push ao mudar status (story futura). Atribuição de etapa para outro usuário (escopo da Story 1.2). Comentários por etapa.

## Riscos
- **Duplo clique em botões:** Pode gerar transições duplicadas. Mitigação: desabilitar botão durante a requisição (loading state).
- **Lógica de "atrasada":** Baseada na data do servidor, não do cliente. Mitigação: sempre calcular no Server Component ou API.
- **Tabela audit_logs existente:** Schema pode ter campos obrigatórios não cobertos. Mitigação: verificar estrutura antes de inserir.

## Story
**As a** operador,
**I want** avançar o status de cada etapa de produção,
**so that** o time saiba o que está em andamento, o que foi concluído e o que está atrasado.

## Acceptance Criteria
1. Página `/produtos/[id]/etapas` lista todas as etapas do produto com status visual (badge colorido)
2. Botão "Iniciar" disponível para etapas com status `planejada` → muda para `em_andamento`, registra `data_inicio_real` e `responsavel_id`
3. Botão "Concluir" disponível para etapas `em_andamento` → muda para `concluida`, registra `data_fim_real`
4. Etapa marcada automaticamente como `atrasada` quando `data_fim_plan` passa sem conclusão (verificação no carregamento da página)
5. Histórico de transições visível por etapa (quem iniciou, quem concluiu, quando)
6. Status geral do produto atualizado: percentual de etapas concluídas exibido no topo da página

## Dev Notes

**Tabelas:** `mvp_stages` (status, datas reais, responsavel_id). `audit_logs` já existe no projeto — reutilizar para histórico de transições.

**Auth:** `getServerSession()` para obter `user_id`. Verificar que `product.user_id = auth.uid()` antes de permitir alterações.

**Status values:** `'planejada'`, `'em_andamento'`, `'concluida'`, `'atrasada'` (atrasada é calculada, não persistida como status principal ou pode ser persistida — decisão do @dev).

**API Route:** `app/api/mvp/stages/[id]/route.ts` com PATCH handler.

**Optimistic UI:** Para melhor UX, atualizar o estado local imediatamente e confirmar com o servidor. Usar `useTransition` do React 19 ou `useState` com rollback em caso de erro.

**Auditoria:** Projeto tem `audit_logs` existente. Inserir registro de mudança de status seguindo o padrão da tabela existente.
